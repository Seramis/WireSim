# Hd44780

Model register-level behavior of HD44780-compatible character LCD controller (`docs/HD44780.pdf`; `docs/LCD1602.pdf` and `docs/LCD2004.pdf` document two glass modules chip ship in). One class cover both modules through `Hd44780Variant::Lcd1602` (16x2) or `Hd44780Variant::Lcd2004` (20x4). Controller, instruction set, 80-byte DDRAM and 64-byte CGRAM same. Only row and column count and address-to-visible-cell mapping differ, that constructor parameter.

## Pins

| Pin | Direction | Notes |
| --- | --- | --- |
| `DB` | in/out, 8-bit | DB0-DB7. Only DB4-DB7 carry data once Function Set pick 4-bit mode (DB0-DB3 float). |
| `RS` | in | 0 = instruction/busy-address register, 1 = data register |
| `RW` | in | 0 = write, 1 = read |
| `E` | in | enable strobe; only real-chip pin that register triggers |
| `BL` | in | backlight enable, active high. **Not** real HD44780 pin (see "Backlight"). |

## Instruction set

All eleven HD44780U instruction (`ExecuteCommand` in `Hd44780.cpp`) implemented: Clear Display, Return Home, Entry Mode Set, Display On/Off Control, Cursor/Display Shift, Function Set, Set CGRAM Address, Set DDRAM Address, Read Busy Flag & Address, and Write/Read Data to/from CG or DDRAM. Decode walk DB7 down to DB0, take first set bit, mirror datasheet Table 6, where each instruction got unique topmost bit.

Function Set `N` and `F` bits (line count, 5x8 vs. 5x10 font) get read but not stored. Row and column count fixed by `Variant`, like glass module silkscreen, cannot change from firmware. Only `DL` (8-bit vs. 4-bit interface) got effect.

## DDRAM addressing

DDRAM flat 128-byte array, addressed direct by 7-bit address counter (`_ac`), match chip `1AAAAAAA` "Set DDRAM Address" encoding. On real 2-line chip only two 40-byte range real (`0x00`-`0x27` and `0x40`-`0x67`). This device no special-case gaps (`0x28`-`0x3F`, `0x68`-`0x7F`); they ordinary, normally unused, never-rendered storage. Behavior firmware depend on get reproduced: auto-increment past column 39 do **not** jump to next visible row (well-known "16x2 don't auto-wrap to line 2" behavior). It walk into dead range first, same as real chip.

`VisibleToAddr(row, col, shiftOffset)` and `AddrToVisiblePos(addr, shiftOffset, row, col)` convert between screen cell and raw address, for rendering and cursor placement. Both include current display-shift offset and, for `Lcd2004`, row-pairing quirk below.

### The 20x4 row-pairing quirk

No real 4-row HD44780-class controller exist. 20x4 module multiplex two physical 40-byte DDRAM line across four visible row: row 0 show line 1 column 0-19, row 2 show line 1 column 20-39, row 1 show line 2 column 0-19, row 3 show line 2 column 20-39. `VisibleToAddr` implement this (`line = row % 2`, with `_cols`-sized offset for row 2 and 3), include well-known side effect: shift display on 20x4 module scramble rows against each other, cuz row 0 and 2 (and 1 and 3) share one line shiftable address space. This get reproduced, not worked around.

## CGRAM and character rendering

`_cgram` is 64 byte (8 user-defined character x 8 row). Only bits 4-0 of each byte meaningful (bit 4 leftmost of 5 column), same as datasheet. Character code `0x00`-`0x0F` render from CGRAM; `code & 0x07` pick glyph, cuz datasheet say code `0x00`-`0x07` and `0x08`-`0x0F` alias same eight character.

Code `0x20`-`0x7E` render from `Font5x8`, baked-in 5x8 bitmap font in `Hd44780.cpp` anonymous namespace. It get rasterize from `hd44780.otf` (next to this file) by sample each glyph outline at center of 5-column by 7-row grid. Font ascent and descent (2000/0 in 2000-unit em) place every glyph on grid with no descender space. Row 7 (bottom dot row) therefore always blank, match real CGROM reserved cursor-underline row. `g`, `j`, `p`, `q` and `y` get draw within row 0-6 instead of descend into row 7 like real CGROM; this font-fidelity simplification avoid hand-author descender missing from source font.

Anything else (`0x10`-`0x1F`, `0x7F`-`0xFF`, where real CGROM got Japanese katakana and extra symbol) **not modeled** and render blank.

## 4-bit nibble protocol

`DL=0` (Function Set) turn `_fourBitMode` on. From then til next `DL=1`, every register access (instruction, data or busy/address read) take two `E` pulse, high nibble on DB7:4 first (`CommitPulse` `_nibblePhase` state machine).

This include single-nibble `0010` handshake that switch assumed-8-bit chip into 4-bit mode. Device still in 8-bit mode when that write arrive, so get read as complete 8-bit Function Set, and `DL` bit position correct whether read as full byte or as 4-bit mode high nibble. No special case need (datasheet Figure 24 explain why this work on real hardware too). Datasheet robustness procedure (send `0011` three time before final `0010`) unnecessary here, cuz model always start from defined reset state. Single correct Function Set work first try.

## Why `E` has both an immediate and a stable trigger

`E` get register twice (`Trig::EImmediate`, `Trig::ECommit`), unlike most device, which pick one kind per pin:

- Drive read data (and release `DB` otherwise) must be **immediate**. Got to be visible in same settle pass where `E` and `RW` change, so script or firmware that raise `RW` and `E` together in one `step` see valid data that step. Stable-only trigger would delay drive to next cycle immediate phase (`overview.md`, "Finality"), break read that must complete within `E` pulse.
- Commit write (or advance address counter after read) must be **stable** and fire exactly once per complete pulse. Commit twice would double-advance address counter and, in 4-bit mode, desync nibble phase.

Two trigger can't share one `_lastEHigh`-style flag, cuz immediate handler bookkeeping would race stable handler edge detection, depend on which phase of cycle run first. Each got own state. `_lastRs`, `_lastRw` and `_lastCaptured` get refresh by immediate handler whenever `E` read high (final refresh before `E` fall what matter). `_pulseActive`, previous-level flag stable handler edge-detect against, touched *only* inside stable handler, so two never clobber each other.

## Backlight

`BL` this device one deliberate addition to real HD44780 interface. Real chip `LED+` and `LED-` bare power pin for backlight LED, which firmware don't switch. Many breakout board switch backlight through transistor on spare digital pin, so `BL` model that common pattern as active-high enable, which `DeviceHarness` could not represent with bare power pin. It got own immediate trigger (`Trig::Backlight`) and get mirror into `std::atomic<bool>` that render thread read. One writer (`Logic()`) and one reader (render thread), so relaxed load and store need no mutex.

## Window, rendering and threading

Render thread start with no window, create one on `OpenWindow()`, can close and reopen freely. It own SDL init/quit refcounting, mutex and thread (`SdlAcquire`/`SdlRelease` in anonymous namespace). Only piece shared with other windowed device `SdlEventHub`, cuz SDL event queue process-global and every window-owning device render thread must poll through it (see `SdlEventHub.md`).

Model state (`_ddram`, `_cgram`, `_ac`, display, cursor and blink flag, shift offset) live in plain member owned exclusive by sim thread. It get copy into `RenderSnapshot` (guard by `_stateMutex`) at end of every complete `E` pulse: dirty-flag, copy-on-write handoff to render thread. All field bundle in one struct, cuz LCD state small (under 200 byte) and change far less often than framebuffer.

Each character cell render as 5x8 grid of individually colored square dot, not blank background with glyph outline. This visual signature of passive-matrix character LCD, where "off" dot stay faintly visible against backlight. Cursor underline (`C` bit) and blink (`B` bit, toggle on wall-clock timer in render thread) get draw over cell at address counter visible position. Both gated on Display On (`D`) bit, per datasheet ("Sets entire display (D) on/off").

Both color scheme (`Hd44780ColorScheme::GreenDark`, `BlueWhite`) draw dimmed, desaturated palette when `BL` low instead of toggle brightness, cuz real transflective STN LCD stay weakly visible by reflect light without backlight power.

## Known simplifications

- **Busy flag always read 0.** No internal-operation timing modeled. Every instruction, even Clear Display (up to 1.52 ms on real silicon), complete within `Logic()` call that commit it. Firmware that poll BF before every instruction never see it set, and fixed-delay loop work identically.
- **Clear Display reset display-shift offset.** Datasheet state this only for Return Home. Clear Display do same so cleared screen don't show blank column in stale shifted position.
- **Cursor/Display Shift cursor-move case don't force DDRAM addressing.** Datasheet call cursor movement over CGRAM address "meaningless" without define effect. This device adjust address counter within whichever address space (CGRAM or DDRAM) selected instead of invent implicit switch to DDRAM.
- **CGROM beyond ASCII `0x20`-`0x7E` not modeled** (see "CGRAM and character rendering"), and `Font5x8` get rasterize wholesale from `hd44780.otf`, not tune per glyph.
- **`N`/`F` (Function Set) got no effect.** Row and column count fixed by `Variant`, only 5x8 font get render.

## Verification

`Hd44780.devtest` (`DeviceHarness`) cover 8-bit instruction decode (entry mode, display control, DDRAM addressing, busy/address readback without disturb AC), DDRAM write and read-back with address counter auto-increment, CGRAM custom-character round trip, and 4-bit nibble protocol (mode switch, two-nibble addressing, two-nibble write, two-nibble read). `Lcd2004` row-pairing mapping (`0x94` = row 2) get check ad hoc against `Lcd2004` instance, not in committed script.

Hd44780 inherit `SdlUiTestHooks` (`src/Support/SdlUiTestHooks.hpp`), so script can use `screenshot <path>` verb (see `SdlUiTestHooks.md`). `Hd44780.devtest` deliberately don't call `screenshot`: rendered frame for human to look at, not deterministic pass/fail check (`SdlUiTestHooks.md`, "Recording, not regression"). Four `Hd44780.screenshot-*.png` file next to this doc (green and blue, lit and unlit) reference capture for reviewer who ain't build simulator, not maintained, auto-refreshed set. `click` not exercised, cuz device got no clickable UI.
